# MiniOneRec SFT 效果诊断与调优过程记录

> 截止日期：2026 年 10 月 22 日（北京时间）。
>
> 当前进度：首次完整 SFT、完整验证集评估、预测审计、解码检查、参数抽查和训练集抽样检查均已完成。128 条样本的 BF16/FP32 短程对照已完成并收到汇总；FP32 组拟合更好；完整三任务FP32参数SFT也已完成，完整valid收益已复算验证，见第12节。
>
> **完整valid已观察到精度调整收益；唯一根因、多seed稳定性与test效果仍未确定。本文保留失败过程及证据边界。**

## 1. 为什么要记录这次过程

项目目标是基于 MiniOneRec，完成 Semantic ID → SFT → GRPO → 推荐评估，并在公平对照中验证一项个人优化。

首次 SFT 完成后，我们发现：训练正常结束、模型可以生成合法 SID，但全量推荐指标不理想。因此先暂停推进 GRPO，围绕以下问题诊断：

1. 指标是否计算正确，预测是否与样本对齐？
2. 是否只是小样本评估造成的误判？
3. SID 碰撞是否影响指标解释？
4. 约束解码是否错误地限制了候选范围？
5. 模型参数是否真的发生更新？
6. 问题是否也出现在训练样本上？
7. 小样本、单任务条件下，参数精度是否影响拟合？

这份记录用于后续实验复盘和面试技术讲解。它不是最终效果报告。

原始推荐行数与混合训练样本数不同，因为除了序列推荐，还构造了物品对齐任务。

### 2.2 三类训练任务

实际由 `sft.py` 拼接以下 Dataset：

| 任务 | 输入 → 输出 | 代码 |
|---|---|---|
| 下一物品推荐 | 历史 SID → 下一物品 SID | `data.py: SidSFTDataset` |
| 物品语义对齐 | SID → 标题；标题 → SID | `data.py: SidItemFeatDataset` |
| 推荐与文字语义结合 | 历史 SID → 下一物品标题 | `data.py: FusionSeqRecDataset` |

当前 FusionSeqRecDataset 实际启用标题任务，描述任务的随机选择分支被注释。三类任务均采用因果语言模型 SFT：prompt 的 labels 为 `-100`，答案和结束标记参与损失。

正式 SFT 前已将 next-SID 的训练/评估 prompt 措辞对齐。该修改不改变训练目标。

## 3. 第一阶段：从流程检查走向真实效果评估

### 3.1 先跑 32 条，验证模型能否正常评估

最初在 valid 抽样 32 条，主要检查：模型可重载、tokenizer 匹配、能输出 Top-10，以及指标脚本可用。

| 指标 | 32 条结果 |
|---|---:|
| HR@5 / HR@10 | 12.50% / 18.75% |
| NDCG@5 / NDCG@10 | 0.107209 / 0.126023 |
| 无效 / 缺失 / 重复候选比例 | 均为 0 |

**判断：** 这只是流程检查，不能拿来代表完整验证集效果。抽样小、目标分布与 SID 碰撞占比都可能影响结果，因此继续做全量 valid。

### 3.2 完整 valid 显示效果不足

统一协议：同一 final checkpoint、同一 prompt、确定性 constrained beam search、beam10、batch1、最多生成 16 token、prompt 上限512，无历史物品过滤、不压缩原始排名。

| 指标 | 完整 valid 4,532 条 |
|---|---:|
| HR@5 | 173/4532 = 3.8173% |
| HR@10 | 251/4532 = 5.5384% |
| NDCG@5 | 0.035078 |
| NDCG@10 | 0.040476 |
| 无效 / 缺失 / 重复候选比例 | 均为 0 |
| 被截断的 prompt | 0 |
| 评估总耗时 | 548.58 秒，约 9 分 9 秒 |
| CUDA peak allocated / reserved | 3.00 / 3.10 GiB |

单目标条件下，HR@K 表示真实目标 SID 是否在前 K 名；命中时 NDCG 为 `1/log2(rank+1)`，未命中为 0，再对查询求平均。

### 3.3 加入简单参照，判断 SFT 是否学到有效推荐规律

使用同一 valid、同一 SID 评分口径，补算两项 CPU 参照：

- 训练集热门：按 train 目标 SID 频次降序，给所有查询返回相同 Top-10。
- 最近交互＋热门补齐：把最后一个历史 SID 放在首位，再以训练热门 SID 去重补齐。

候选构造不使用 valid 目标标签。

| 方法 | HR@5 | HR@10 | NDCG@5 | NDCG@10 |
|---|---:|---:|---:|---:|
| 训练集热门 | 0.046778 | 0.056708 | 0.042165 | 0.045369 |
| 最近交互＋热门补齐 | 0.075243 | 0.082966 | 0.068946 | 0.071407 |
| 当前 SFT | 0.038173 | 0.055384 | 0.035078 | 0.040476 |

**结论：** 当前 SFT 在这些聚合指标上没有超过简单参照；没有证据支持“训练成功就代表推荐有效”。未进行配对显著性检验，不将数值差距写成统计显著结论。

证据：[完整 valid 与参照记录](experiments/E1_VALID_20261021.md)、[CPU 参照结果](experiments/HEURISTIC_VALID_20261021.json)。

## 4. 第二阶段：检查指标口径、预测对齐和候选集中度

### 4.1 SID 命中不总是唯一物品命中

3,686 个物品对应 3,670 个 SID，存在 15 组 SID 碰撞，涉及 31 个物品。完整 valid 中有 238 条目标 SID 对应多个物品。

- Top-10 共命中 251 条，其中 153 条来自碰撞目标组。
- 4,294 条唯一目标 SID 查询的 HR@10 为 98/4294 = 2.2823%。

**判断：** 原始 SID 指标需要连同碰撞分组解释。不能把全部碰撞组命中视为错误，也不能把 SID 命中直接称为严格 item-level 命中。暂未通过重建 SID 解决碰撞。

### 4.2 收到逐条 predictions 后，先检查是否评错对象

执行 `scripts/audit_predictions.py`：

1. 检查 `source_row_index` 有效且不重复。
2. 对照本地 valid CSV 的 user、target item、target SID。
3. 按历史 SID 重建完整输入文字并逐条比对。
4. 重新计算 HR、NDCG、无效/缺失/重复比例。

**结果：** 4,532 条全部对齐，全 valid 覆盖，指标完全复现。

**证据边界：** 排除了本次所检查的样本错位和指标复算错误，没有据此宣称整个数据预处理不存在任何泄漏或分布问题。

### 4.3 核心发现：候选高度集中

| 现象 | 完整 valid |
|---|---:|
| 所有 Top-10 位置总数 | 45,320 |
| 合计不同预测 SID | **28** |
| 覆盖目录 SID 的比例 | **0.763%** |
| 不同 Top-1 SID | **4** |
| 最常见 Top-1 | `<a_107><b_93><c_0>` |
| 该 SID 排第一的查询数 | **2,782/4,532 = 61.39%** |
| 不同的有序 Top-10 列表数 | 418 |

**判断：** 模型对不同历史的推荐高度集中，但并不是所有历史的输出完全相同，不能断言模型完全忽略历史。

据此把后续诊断重点从“换大模型、直接加 RL”转向“候选是否被限制，以及模型是否有效拟合”。

证据：[完整 valid 逐条审计](experiments/E1_VALID_FULL_20261021_audit.json)。

## 5. 第三阶段：核查约束解码和参数更新

### 5.1 假设一：合法物品被约束代码错误挡住

**为什么提出：** 无效 SID 为 0 只说明已生成结果合法，不证明全部合法 SID 都允许生成。候选少也可能来自解码规则错误。

**检查方法：** 新增 `scripts/diagnose_sft.py`，读取保存的 tokenizer/config，从真实 `evaluate.py` 抽取约束表构建与 callback，检查每个目录 SID 的路径；另用真实 `ConstrainedLogitsProcessor` 抽查各生成步的 CPU 张量掩码。

第一次诊断报 `IndexError ... got set`。这是诊断脚本漏抽取集合转列表循环造成的，**不是原评估解码代码的故障**。补全抽取并增加返回类型回归测试后重跑。

第二次结果：

| 检查项 | 结果 |
|---|---:|
| 检查的不同 SID | 3,670 |
| 被阻断的目录路径 | **0** |
| 后缀长度，含 EOS | 所有 SID 均为 5 token |
| 真实 processor CPU 掩码检查 | **100 项通过** |

**结论：** 没有发现被检查的目录约束路径被错误封锁。该结论不排除有限 beam 的搜索损失，也不覆盖生成框架所有细节。

### 5.2 假设二：训练参数没有有效更新

**为什么提出：** 当前代码以 BF16 加载参数，再使用 AdamW 和 2e-5 学习率。参数存储精度、计算精度、优化器状态精度不是同一回事，值得检查实际更新。

**检查方法：** 用 safetensors 在 CPU 读取基座与 final checkpoint 的少量矩阵行，以及完整最终 norm，比较数值变化。不是加载全部模型或统计全部参数。

| 位置 | 抽查不变元素比例 | 相对 RMS 变化 |
|---|---:|---:|
| 第 0 层 `q_proj.weight` | 84.16% | 0.717% |
| 第 10 层 `mlp.down_proj.weight` | 80.97% | 1.101% |
| 第 27 层 `o_proj.weight` | 79.43% | 1.472% |
| 最终 `model.norm.weight`，1,536 元素 | 100% | 0 |

两侧存储 dtype 均为 BF16。

**能够确认：** 所抽查的三处主干权重有变化，不能说整个模型完全没训练或完全没保存。

**尚不能确认：** 不变元素多就是异常；最终 norm 没变化就是被冻结；BF16 舍入就是效果差的根因。检查未覆盖原训练的实际 optimizer state、每一步梯度和全部新 SID embedding 更新。

证据：[诊断说明](SFT_DIAGNOSIS.md)、[首次诊断含报错](experiments/E1_SFT_DIAGNOSIS_20261021_v1.json)、[修正后诊断](experiments/E1_SFT_DIAGNOSIS_20261021_v2.json)。

## 6. 第四阶段：回到训练集，检查见过的样本表现

### 6.1 为什么做 train-256

如果只看 valid 很差，很容易直接归因过拟合。先用相同 checkpoint 和相同生成协议，在原 train 随机抽 256 条，看看候选集中是否也发生在见过的样本上。

这一步只有推理，没有新增训练。

### 6.2 实际结果

逐条对照 train CSV，256 条全部对齐，指标复算一致。

| 指标 | train-256 | 完整 valid |
|---|---:|---:|
| HR@5 | 14/256 = 5.4688% | 3.8173% |
| HR@10 | 16/256 = 6.2500% | 5.5384% |
| NDCG@10 | 0.044048 | 0.040476 |
| 全部 Top-10 不同预测 SID | **24** | **28** |
| 不同 Top-1 SID | **4** | **4** |
| 最常见 Top-1 占比 | 67.58% | 61.39% |

train-256 实际有 233 个不同目标 SID。相同 256 条上的训练热门参照 HR@10 为 14/256，SFT 为 16/256；这一小幅差距不足以证明有效优势。

**结论：** 候选集中不是只出现在 valid。接下来优先检查训练拟合与更新，而不是直接宣称过拟合。

**限制：** 两个数据集合大小、分布不同，不能拿这张表精确估计泛化差距；推荐目标有不确定性，相同历史也可能有不同目标，低训练 HR 本身不证明代码出错。

证据：[train-256 记录](experiments/E1_TRAIN256_20261021.md)、[逐条审计](experiments/E1_TRAIN256_20261021_audit.json)。

## 7. 已完成：128 条单任务拟合与精度对照

### 7.1 选样目的与规则

为减少真实推荐中的目标歧义，先构造一个容易解释的小样本任务，检查训练流程有没有基本的学习能力。

- 只使用原 train，不读取 valid/test 标签。
- 以历史 SID 序列为 key，排除全 train 中对应多个目标 SID 的历史。
- 对其余重复历史保留第一条代表，seed42 抽 128 条。
- 本地实际选出了 **128 条样本、125 个不同目标 SID**。
- 保存原 train 行号、样本 CSV 与哈希。

全 train 有 30,016 个不同历史，其中 1,550 个有冲突，28,466 个符合选样条件。这是为了诊断而筛选的子集，不代表真实推荐分布。

### 7.2 对照配置

| 条件 | 初始参照 | A 组 | B 组 |
|---|---|---|---|
| 起点 | 当前 E1 final checkpoint | 同一 E1 | 同一 E1 |
| 新增训练 | 无 | 100 updates | 100 updates |
| 参数精度 | 原模型 BF16 | BF16 | FP32 |
| 前向计算 | BF16 推理 | BF16 autocast | BF16 autocast |
| 任务 | 对128条生成推荐 | 仅历史→下一 SID | 同左 |
| 优化器 | 不适用 | 新建 AdamW | 新建 AdamW |
| LR / 调度 | 不适用 | 2e-5 / constant，无 warmup | 同左 |
| 有效 batch / micro / 累积 | 推理 batch1 | 32 / 2 / 16 | 同左 |
| 数据顺序与 seed | 固定子集 | seed42 | seed42 |
| 生成评估 | beam10 | BF16 导出后 beam10 | BF16 导出后 beam10 |

B 组不是从 A 组接着训练。两组都继承 E1 已学到的知识，但不继承其 optimizer state。

**为何暂时去掉标题任务：** 降低诊断复杂度，先确认 next-SID 任务能否拟合。这不是证明标题任务无用，也不是正式删除它的消融结论。

### 7.3 自动记录什么

1. 实际 Dataset 的训练/推理 prompt 对齐、label mask、SID 三 token 与换行/EOS 监督是否完整。
2. 每组第 10 步的耗时、峰值显存、实际 optimizer state dtype。
3. 前后目标 token NLL，包含换行与 EOS。
4. a/b/c 各层 teacher-forced NLL、top1/top10 准确率。
5. 主干抽样、完整最终 norm、当前目标 SID embedding 行的变化。
6. 相同 BF16 推理条件下的 HR/NDCG/invalid、不同预测 SID 数与 Top-1 分布。

Teacher forcing 中 b、c 会看到真实前缀；分层准确率不能冒充自由生成准确率。两组都导出 BF16 后评估，内存中 FP32 参数计算的训练诊断值与导出后的生成值分别保存。

### 7.4 资源安排与当前状态

- 单卡 A800 80GB，使用现有环境和现有 SFT 权重。
- 两个模型导出约增加 6 GiB，脚本要求开始前至少 10 GiB 空闲磁盘。
- 第 10 步若 reserved 超过 60 GiB，或推算单组训练耗时超过 1,800 秒，则报错停止；不是完整运行资源上限的保证。
- 原 E1 不覆盖，输出为独立时间戳目录，最终汇总为 `comparison.json`。
- 本地通过真实数据选样、语法检查与 CPU 单测。
- **已收到 comparison 汇总，两组均完成100步；尚未收到独立的 step10 profile 和逐条预测。结果见下一节。**

代码版本：`0b1941c`。运行说明：[128条诊断操作文档](TINY_SFT_DIAGNOSTIC.md)。

### 7.5 实际结果与结论更新

| 指标，同一128条train样本 | 初始E1 | BF16参数组 | FP32参数组 |
|---|---:|---:|---:|
| HR@10 | 5/128=3.9063% | 34/128=26.5625% | 44/128=34.3750% |
| NDCG@10 | 0.022933 | 0.119190 | 0.172745 |
| 不同Top-10预测SID | 24 | 117 | 133 |
| 不同Top-1 SID | 4 | 14 | 18 |
| 最高频Top-1占比 | 76.56% | 25.00% | 17.19% |
| 最终目标token NLL | 约2.915 | 2.148497 | 1.997043 |

两组报告的样本哈希和受控训练条件一致；FP32组训练前NLL约2.919，与BF16组略有数值差异。三组生成指标均在BF16推理下获得。FP32组训练耗时149.07秒、peak allocated 28.83 GiB；BF16组131.78秒、14.41 GiB。FP32开销在A800上可承受。

**新结论：** 两组都能学，FP32参数组在本次小样本条件下拟合更好；结果支持进一步验证精度配置的影响，不证明原始完整训练的唯一根因或valid收益。参数与相关优化器数值行为尚未分离，不能只归因为参数舍入。不能用128条训练记忆指标替代完整推荐评估。

仅收到汇总，未独立重算本次逐条预测，未做多seed或配对显著性检验。详细结果与边界见[实际对照记录](experiments/TINY_SFT128_20261021.md)、[原始汇总](experiments/TINY_SFT128_20261021_comparison.json)。

下一项建议是从原始Base重新运行完整三任务SFT的FP32参数对照，保留原E1、数据与超参，先profile，再以完整valid验证。**尚未启动。**

| BF16 更新受限 | 保存权重为 BF16，不变元素多、norm 未变 | 小样本对照支持精度影响拟合；完整训练根因未确诊 |
| 仅为验证集过拟合问题 | 训练抽样同样候选集中 | 不能简单这样解释 |
| 模型容量不足 | 没有受控模型规模对照 | 未证实，暂不换基座 |
| 多任务配比或训练配置不合适 | 当前只知道混合任务及其结果 | 仍待验证 |
| beam 宽度不足 | 尚无同模型宽度对照或精确候选排序对照 | 未排除，未作为首个调参动作 |
| SID 碰撞影响指标解释 | 已量化碰撞目标及分组命中 | 已确认口径问题，未证明是集中现象根因 |

没有补做原始基座的 SID 指标：基座尚未学习新增 SID；该实验可回答训练前后变化，但不是当前优先的推荐参照。

## 9. 如何进入正式调优

以下为决策规则；首项已有小样本证据，完整SFT对照尚未执行。

| 128条结果 | 下一行动 |
|---|---|
| FP32 组在相同预算下明显改善拟合 | 核查实际 dtype/更新证据，再设计完整 SFT 的精度对照 |
| 两组都能明显改善拟合 | 回到完整数据的学习率、任务配比、训练步数及推荐分布 |
| 两组都改善有限 | 继续查梯度、mask/目标、学习率和训练预算，不能立即归因容量 |
| teacher-forced 指标改善而生成仍集中 | 检查自由生成误差、概率分布、beam 搜索与训练/推理差异 |
| 资源门槛或运行报错 | 保留日志，先修复或调整可行性配置，不启动完整重训 |

若选定正式修改：保留原 E1，对相同完整数据、SID、评估协议运行受控新 SFT；记录 valid 效果、候选覆盖、碰撞口径、耗时及显存。只有改善在完整实验中得到验证后，才能称为有效调优。

SFT 评估稳定后，再处理原版 GRPO 的样本目标映射等既知工程问题，进入 SFT vs 原版 GRPO vs Reward 改进对照。Test 留待方案冻结后评估。
